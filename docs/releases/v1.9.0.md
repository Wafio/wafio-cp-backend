# Wafio v1.9.0 release notes

Status: released 2026-10-17 from `main` (tag `v1.9.0`). Previous release: [v1.8.2](v1.8.2.md) (2026-10-16).

A resource release. Host agents send about 40× less telemetry to the control plane, the database
keeps telemetry older than a day compressed (about 3× smaller overall on the demo host, 4–15× per
table), and the control plane and host agent use less CPU. WAF decisions no longer store
credentials from request headers, query strings and request bodies, and three kinds of false-positive
incidents are fixed (see below). No change to what is detected.

## Upgrade

Order: control plane (it runs migrations 000112, 000113 and 000114) → host agents → WAF agents. The only
WAF agent change is the decision redaction below. Every mix of versions works:

- a v1.9.0 host agent under an older control plane sends uncompressed telemetry and its
  snapshots every 3 s, as before;
- an older host agent under a v1.9.0 control plane is served as before;
- decisions from an older WAF agent are redacted by a v1.9.0 control plane when they arrive.
  Such an agent does not send `match_source_exact` (new `WAFDecisionEvent` field 25), so its
  match sources count as guesses: a credential-named input keeps no value, even when it held
  the payload. Upgrade WAF agents to keep that evidence.

The savings start once both the control plane and the host agent run v1.9.0.

- **Migration 000112** compresses the five telemetry hypertables (`waf_decisions`,
  `host_security_events`, `host_fw_features`, `host_sec_features`, `host_enforcement_events`).
  - The migration only changes settings and is quick.
  - A TimescaleDB background job then compresses the existing chunks older than a day. On the
    1-vCPU demo host the five jobs took about 80 s in all for 1 GB (the longest 35 s).
  - It needs TimescaleDB 2.11 or later under its community license (`timescaledb.license =
    'timescale'`), which the installer sets up. Otherwise the migration skips compression with a
    notice and the tables stay as they were.
  - Rolling back the schema (`migrate down`) decompresses everything again and needs the disk
    space for it; a rollback can keep the schema instead (see [Rollback to v1.8.2](#rollback-to-v182)).
- **New proto field.** `CommandAck.payload` (field 4) carries the compressed telemetry. It is
  only sent to a control plane that announces it, so older control planes never see it.
- **Retention now also runs without TimescaleDB policies.** On plain PostgreSQL (or a
  TimescaleDB under the Apache license) old telemetry was never deleted. From this release the
  control plane deletes rows older than the retention (defaults 30 days, `host_security_events`
  7 days) every hour. The first deletion waits one hour after the control plane first starts
  on v1.9.0 (the page shows "Retention starts at … UTC"); raise the retention under
  Administration › Data retention within that hour if you want to keep more. Restarts do not
  restart the wait. A save during it applies when it ends.

## Rollback to v1.8.2

The installer only installs the latest release and keeps no copy of what it replaces. Before
upgrading, keep a `pg_dump` of the database and a copy of `/usr/local/bin/wafio*`,
`/opt/wafio/frontend` and `/opt/wafio/migrations` (or the v1.8.2 bundles). Agents do not have to
go back: v1.9.0 agents under a v1.8.2 control plane work as described under Upgrade.

- **Control plane binary only (recommended).** Stop the control plane, put the v1.8.2 `wafio`
  binary and frontend back and start it. Leave the schema at 114. Do not run v1.8.2's
  `wafio migrate up`, `serve --migrate` or its installer: they stop with `no migration found
  for version 114` and change nothing. On schema 114, v1.8.2:
  - reads compressed chunks as before; TimescaleDB keeps compressing chunks older than a day,
    because the policy is stored in the database;
  - keeps applying the two new built-in trace rules (they are rows like any other rule);
  - leaves retention to the TimescaleDB policies, which keep the values saved on the Data
    retention page. On PostgreSQL without TimescaleDB old rows are no longer deleted, as before
    v1.9.0;
  - ignores the new `server.agent_recv_*` settings in `config.yaml`.

  Upgrading again is a normal v1.9.0 install.
- **Schema too.** With v1.9.0 still installed and the control plane stopped, run
  `wafio migrate down --steps 3 --migrations /opt/wafio/migrations`, then put v1.8.2 back.
  - 000112 decompresses every chunk. It needs free disk for the uncompressed size
    (`before_compression_total_bytes` of `hypertable_compression_stats('<table>')` for each of
    the five tables) and takes a while on a large database.
  - 000113 and 000114 remove the two new built-in trace rules.

Tested (2026-10-17), each time: the v1.8.2 control plane on schema 114, then after
`migrate down --steps 3`, then upgraded to v1.9.0 again; nothing was logged as an error.
- On a copy of the demo data (TimescaleDB 2.x, 104 compressed chunks, 1,031 MB uncompressed,
  305 MB compressed): WAF decisions, trace events, incidents and the overview read normally
  on compressed chunks. `migrate down --steps 3` took 80 s on 1 vCPU and left every row
  unchanged (per-table checksums equal before and after), and so did compressing again.
- On PostgreSQL 18 without TimescaleDB: login, projects, hosts, trace and correlation rules.

## No credentials in WAF decisions

A WAF decision used to carry every request header except `Authorization`, `Cookie`,
`Set-Cookie` and `Proxy-Authorization`, and the whole query string. API keys, CSRF and session
tokens, signed-URL signatures and passwords in a query string were stored in `waf_decisions`,
shown in the decision drawer, streamed to the dashboard and, in the URI, sent to the SIEM.

- Header, query parameter and cookie values with a credential name are replaced with
  `[redacted]`; the name stays. The names: `key`, `sig`, `auth`, `pass`, `ticket` (also with
  `x-`), any name with the word `pwd`, `pw`, `sid`, `otp` or `totp`, and any name containing
  `token`, `secret`, `password`, `passwd`, `passphrase`, `apikey`, `accesskey`, `privatekey`,
  `signature`, `hmac`, `credential`, `session`, `sessid`, `csrf`, `xsrf`, `jwt`, `bearer` and a
  few other `…key` names, `code` (OAuth authorization code), `pin`, `passcode`, `SAMLResponse`
  and `SAMLRequest` (case and `-`/`_`/`.` ignored, so `X-API-Key`, `accessToken`,
  `X-Amz-Security-Token` and `PHPSESSID` all match). Query parameters separated by `;`
  (`?x=1;token=…`) and path parameters (`/app;jsessionid=…`) are covered. `Referer` and similar
  URL headers get the same treatment for their query string and path parameters.
- Request bodies: the body preview (512 characters) and the stored request body (first 4 KiB)
  get the same treatment field by field — form fields, JSON keys at any depth (case ignored;
  everything under a credential-named key, nested objects and arrays included) and multipart
  text fields. A login form's password is no longer stored. Both copies are cut prefixes: a
  field cut by the prefix is still redacted. XML and other bodies are stored as sent.
  Card numbers, CVV/CVC and SSN fields (`cardnumber`, `creditcard`, `ccnum`, `cvv`, `cvc`,
  `ssn`) now count as credential names too.
- The input that triggered the detection (`match_source`) keeps its value when the engine
  named that input itself (`match_source_exact`): a semantic engine flagged that header, query
  parameter, form field or JSON key (`match_source` `body.json:<key>` for a JSON field). A
  content-scan match on an upload is not exact (the file bytes are not stored, and a same-named
  text field must not keep its value). Only the exact markers the redactor writes count as
  already redacted. Its value is kept whatever it looks like — a
  `?code=__import__('os').system('id')` or a `/etc/passwd` in a password field is evidence.
  Limits: a credential check — the JWT engine, the entropy anomaly heuristic — can flag a real
  credential, so then only a JWT's header segment (`eyJhbGciOiJub25lIn0.[redacted]`) or the
  value's length (`[redacted:len=24]`) is kept; `Authorization` always keeps only its scheme
  and, for a JWT, the token header; a credential header with several comma-separated values,
  a parameter or field that occurs more than once (`query:hpp:`) and the Cookie header as a
  whole keep only the values that look like an attack; a `Referer` still has its credential
  parameters redacted, except one that holds the payload. Only a real field value is named
  exactly: the batched or unusual JSON key summary (`body.json:key`), operator members
  (`…:op`), joined leaves (`body.json:joined`), form names, leaves of JSON inside a form field,
  array elements and whole-document sources are not, so `{"key":"AIzaSy…","x<script>…":"y"}`
  no longer keeps the `key` field. The WAF agent also knows the flagged value (in memory only,
  never sent) and keeps a credential-named field only when it holds that value: a victim's
  `token` next to an injected `token`, under an escaped (`\u0074oken`) or percent-encoded
  (`tok%65n`) name, or ahead of a flagged duplicate past the stored 4 KiB, is redacted. The
  control plane, which never sees the flagged value, keeps only payload-like values when the
  name occurs more than once (names decoded the way the engine decodes them) or the stored
  copy is shorter than the request body.
- A match source that is a guess keeps no credential-named value. A rule-based (CRS) verdict
  does not say which input matched: its `match_source` names the first query parameter whose
  value looks like an attack and whose name is not a credential name, or just `query`. It used
  to name the first parameter (a token there stayed readable), and then any parameter whose
  value tripped a weak marker — a password `Subscription!2024` ("script") or any `%` typed in
  a GET form (`%25`).
- The WAF agent redacts before sending; the control plane redacts again when a decision
  arrives, so decisions from older agents are covered too. This applies to the stored row, the
  live stream, the block list, the SIEM event and the project log, and to the URI and body
  preview of decisions sent to the legacy HTTP ingest (`POST /api/internal/waf/ingest`). The
  SIEM and project log header fields show `Referer` and `Cookie` with every credential value
  redacted; their body snippet gets the body redaction above (multipart fields, `signature`,
  `key`, `pass`, `access_key`, `hmac` … included) with no field kept.
- Rows stored before the upgrade are not rewritten; they leave with the 30-day retention.
- Cost on the WAF agent: about 13 µs (form) and 23 µs (JSON) per 4 KiB body on an M-series
  laptop, once per recorded decision, after the verdict.

## Less telemetry traffic

Measured on the demo host, over 10 minutes each:

| | v1.8.2 | v1.9.0 without forwarding filter | v1.9.0 without status on demand | v1.9.0 |
|---|---|---|---|---|
| Host agent → control plane | 57.9 KB/s at ±42 events/s (±150 GB/month) | 3.2 KB/s at ±37 events/s (±8 GB/month) | 2.1–2.4 KB/s at ±20–58 events/s (±5–6 GB/month) | 1.4 KB/s at ±48 events/s (±3.7 GB/month) |
| Per trace event | 1.37 KB | 0.09 KB | 0.04 KB | 0.03 KB |
| Control plane → host agent | 0.84 KB/s | 0.30 KB/s | 0.30 KB/s | 0.24 KB/s |

With the forwarding filter (below) most of what was left is not trace events: host status, host
info and trace statistics every 3 s and firewall metrics every second, about 1.5–2 KB/s
together. Status on demand (below) sends those only while someone looks. Measured on the demo the same
evening, 10 minutes each with nobody on a host page: 2.18 KB/s at ±30 events/s before, 1.43 KB/s
at ±48 events/s after. Most of what is left is the once-a-second batches of trace events the
control plane stores; a host without events sends little more than the 30 s payloads (not
measured).

What changed:

- **Compressed telemetry batches.**
  - The host agent gzips each telemetry batch (4–20× smaller) once the control plane announces
    that it takes them.
  - The control plane reads the declared size from the gzip trailer and charges it to the
    account's receive budget before inflating, then requires the exact size and a valid
    checksum.
  - A batch may declare at most 64 times its compressed size. Without that limit 8 KB of
    compressed zeros could declare 8 MiB, and an account could claim a full fair share for a
    thousandth of the bandwidth.
  - Real batches stay below the limit: 4–20× normally, 43–62× in floods of near-identical
    events. When a batch would compress more (identical events, long repeated strings), the
    host agent pads it to the limit. Padding inflates to nothing, so no batch is dropped
    because of its ratio. Status counts them in `telemetry_delivery.padded_batches`.
  - Gzip payloads on a stream the control plane never announced gzip to are dropped.
  - gRPC transport compression is deliberately not used: grpc-go inflates a message before any
    check, so 28 KB on the wire could make the control plane allocate 8 MiB.
  - The WAF agent's decisions stay uncompressed: one decision mixes client-chosen request data
    with headers that are not redacted, and compressed sizes would leak them to someone
    watching the link.
- **One batch a second.** The host agent sends a telemetry batch every second instead of
  every 250 ms. HIGH and above, enforced events, kill outcomes and enforcement entries still go
  out within 250 ms, and a full batch still goes at once. Burst capacity is unchanged.
- **Connections and bandwidth on demand.**
  - These snapshots are sent every 3 s only while someone has the Firewall page of the host open,
    and every minute otherwise.
  - The page asks the agent on its first poll.
  - An agent that reconnects while the page is open stays live.
- **Status and metrics on demand.**
  - Host info, eBPF and trace status, trace statistics and rule hit counts are sent every 3 s,
    and firewall metrics every second, only while a page that shows them is open: the
    Firewall or Runtime Security page of the host (stream channels `status`, `metrics`,
    `stats`, `hostinfo`, `connections`, `bandwidth`) or a read of `…/host/status`,
    `…/host/metrics`, `…/host/trace/status` or `…/host/trace/stats`. Otherwise both every
    30 s.
  - The page asks the agent on its first poll and keeps the window open (2 minutes, renewed at
    most every 30 s, one message for a Firewall viewer).
  - The agent still sends its status at once when it connects, when a page opens and right
    after it applies a configuration push (applied generation, bundle status, refusal code).
  - Online/offline is unchanged: the 30 s heartbeat keeps `last_seen`.
  - Database writes drop with it. Every telemetry batch also marked the host seen
    (`hosts.last_seen`); batches now do that at most every 15 s (the first one after a
    connect at once; the offline sweep waits 90 s, the heartbeat touches every 30 s). Measured
    on the demo over 5 minutes with nobody looking, for the host and its WAF agent: 0.39
    updates a second on `agents` and 0.17 on `hosts`, from about 2 and 1.3 with the old
    cadence. With a host page open the agent is back at about 2 a second on `agents`.
  - An older control plane (no `status_on_demand` in `telemetry:demand`) keeps the agent at
    3 s / 1 s, as before.
- **Rule hit counts only when they change.**
  - With the status payload (above), but only for the lists whose counts changed.
  - Every list is sent whole, and all of them every 5 minutes.
- **Receive budget.**
  - Every message an agent stream sends is charged, at its size, to the account that owns the
    project: 64 MiB/s per account, with a burst of one second of it.
  - Gzip payloads are charged again at their inflated size, before inflating.
  - Past the budget, that account's streams read nothing until the debt is paid. Their agents
    slow down and drop noise first. Nothing is refused, and other accounts are not affected.
  - While a stream waits, its agent is still marked as seen every 30 s, so a throttled agent
    does not look offline.
  - The Hello is capped at 64 KiB, and a connection carries at most 16 streams.
- **Process-wide fair share.**
  - The accounts active in the last 2 s share one total of 128 MiB/s.
  - An account alone, or a few that fit in the total, keep their full 64 MiB/s.
  - Under contention every active account gets at least total ÷ active accounts. An account
    sending less gets what it sends without waiting, and what it leaves goes to the others.
  - Owning several accounts no longer adds to what the control plane takes in.
  - Holding a share costs bandwidth. With the 64× limit, squeezing other accounts down to
    total ÷ (k + 1) takes 1.5–2 MiB/s of upload across the k accounts, about what real
    telemetry of that size costs. Before the limit it took about 0.1 MiB/s.
  - Set with `server.agent_recv_account_mib_per_sec` and `server.agent_recv_total_mib_per_sec`
    (MiB/s, 0 = default; the total must be at least the per-account budget, otherwise boot
    stops; restart to change).
  - New series: `wafio_agent_recv_*` on `/metrics` (charged bytes, waits by reason, wait
    time, active and throttled accounts, debt, current share, limits).
- **Status.** Host status now reports `telemetry_delivery.compression` (`gzip`/`none`),
  `resent_batches` and `padded_batches`.

Resources on the demo host (1 vCPU, 5 minutes, after restart):

| Process | CPU v1.8.2 | CPU v1.9.0 | RSS v1.8.2 | RSS v1.9.0 |
|---|---|---|---|---|
| Control plane | 1.47% | 0.81% | 172–182 MB | 121–140 MB |
| Host agent | 2.67% | 1.99% | 156–165 MB | 130 MB |

## Trace events the control plane would discard stay on the host

Most trace events a host agent sent were thrown away by the control plane: on the demo host
about 23 events/s reached the control plane and about 1/s was stored.

- The control plane now sends each v1.9.0 host agent a forwarding filter
  (`trace:forward_filter`), built from that host's trace detection rules and the project's
  correlation chains. A rule or chain change (create, edit, toggle, delete, built-in seeding,
  bulk apply) sends the new filter to connected agents at once, without waiting for their next
  batch. Connected agents are read from memory, not with database queries per agent; a bulk
  apply sends at most one filter per host; one account's changes cannot hold up another
  account's (the sender takes turns per account, at most 64 hosts per turn).
- A filter over 1 MiB is never sent: the agent gets a small `too_large` marker instead, sends
  every event, and its trace status shows `forward_filter: too_large`. The control plane logs
  `trace_forward_filter_too_large` once per rule set.
- The agent runs the same classification as ingest. It holds an event back only when a suppress
  rule drops it, or when no correlation stage matches it and ingest would not store it.
- Rule hit counts of held-back events are reported with each batch, so the hit counts in the
  dashboard do not change.
- Without a current filter the agent sends everything, as before. That covers an older control
  plane, a revision or digest mismatch, the HTTP push path, and a panic in the filter.
- Trace status shows `forward_filter`, `forward_filter_digest`, `forward_filtered_suppressed` and
  `forward_filtered_unstored`. Held-back events are not counted as loss.

## Compressed telemetry tables (migration 000112)

Chunks older than a day are compressed column by column:
- rows are grouped by agent, newest first (`compress_segmentby = agent_id`,
  `compress_orderby = <time> DESC, id DESC`);
- compression is lossless: every table's checksum was the same before and after on a copy of
  the demo data;
- today's chunk is never compressed, so writes and the live views do not touch compressed data.

Measured on the demo host:

| Table | Before | After |
|---|---|---|
| Whole database | 1,038 MB | 366 MB |
| `host_security_events` (2 days) | 198 MB | 13 MB (15×) |
| `waf_decisions` | 39 MB | 8 MB |
| `host_fw_features` | 71 MB | 19 MB |
| `host_sec_features` | 35 MB | 7 MB |

Query speed on compressed data:
- Counting and grouping queries are as fast or faster (count by category 508 → 101 ms).
- Reading "the latest N" from old chunks is up to 2.6× slower, still under 260 ms on 1 vCPU.
- UPDATE and DELETE on compressed chunks work (agent delete cascade), only slower.

## Fewer false-positive incidents

Two incidents on the demo host on 2026-10-16 came from the product itself.

- **The dashboard no longer opens hidden paths.** Scanners asked the control plane for
  `/.aws/credentials`, `/.env`, `/.git/config` and similar. The static file handler looked each
  one up under `server.frontend_path`, and the SPA fallback then answered 200 with
  `index.html`. The host agent saw the control plane open a credentials path and raised a HIGH
  T1083 (Discovery) incident, and scanners took the 200 as a hit.
  - Any path with a segment starting with a dot now answers 404 before a file is looked up. This
    covers encoded (`%2e`), doubled-slash and `..` spellings. The answer is the same whether such
    a file exists or not.
  - Only files that are part of the dashboard build reach the file server. Any other path, such
    as `/etc/shadow` (what nginx forwards for `/%2e%2e/etc/shadow`), is answered without looking
    anything up on disk.
  - Missing files with extensions scanners look for (`.php`, `.bak`, `.sql`, `.env`, `.yml`,
    archives …) also answer 404 instead of `index.html`. Dashboard deep links are unchanged.
- **JIT runtimes no longer raise CRITICAL W^X incidents (migration 000113).** Node.js (OWASP
  Juice Shop on the demo host), the JVM, .NET, PyPy, LuaJIT and Mono map JIT code writable and
  executable at once. The kernel marks every such `mprotect` CRITICAL, so every one opened an
  incident.
  - A new built-in rule, `Downgrade JIT runtime RWX memory`, keeps these events at MEDIUM and
    tags them `jit-runtime`, `unverified-identity`. They are still stored and shown in Runtime
    Security, but open no incident.
  - The process picks its own name, so the rule only lowers the severity. It never drops an
    event. Any other process keeps CRITICAL. Enforced events and completed correlation chains
    are not changed.
  - The event text now reads `W^X violation (JIT runtimes do this; shellcode indicator
    otherwise)` (new host agent).
- **Root regaining root no longer raises HIGH incidents (migration 000114).** logrotate, run as
  root by `logrotate.timer`, sets its effective IDs aside for a `su` rotation and takes them back
  with `setgid(0)`/`setuid(0)`. The kernel rates these HIGH/CRITICAL, so the demo host got a
  HIGH incident every night.
  - A new built-in rule, `Downgrade already-root credential change`, keeps `setuid(0)` and
    `setgid(0)` at MEDIUM (stored and shown, no incident), tagged `already-root`,
    `credential-change`, when the event's real user ID is already 0. Such a request needs no
    privilege and gains nothing. It is deliberately not tagged `expected`: a compromised root
    daemon that dropped its effective IDs looks the same when it takes root back.
  - The rule reads only IDs the kernel records, not the process name. A user running a
    set-user-ID root binary, a service account and root inside a user namespace have another
    real user ID and keep HIGH/CRITICAL. Enforced events, the shell escalation rule and completed
    correlation chains are not changed. Control plane only; no agent update.

## Data retention and database size alert

Administration › Data retention (`/admin/retention`, system admins only). No migration; the
settings are rows in `system_settings`.

- **Retention per table.** `waf_decisions`, `host_security_events`, `host_enforcement_events`,
  `host_fw_features` and `host_sec_features` keep their defaults (30, 7, 30, 30, 30 days) until an
  admin changes them. Minimum 7 days (`host_security_events` 2), maximum 3650, whole days. A
  value that is not longer than the table's compression window (1 day, migration 000112) is
  refused.
- **How it runs.** With TimescaleDB 2.0 or later (community license) the retention policy is
  replaced, in one transaction with the saved setting; a shortened table is trimmed at once.
  Without policies (Apache license) the control plane calls `drop_chunks` hourly. On plain
  PostgreSQL it deletes old rows hourly, 5,000 rows per batch, at most 500,000 rows per table per
  pass, with the cutoff computed on the database clock. Before this release nothing ran on plain
  tables. A stored value outside the table's range (edited by SQL, restored) is never used: that
  table is skipped, logged and shown as not active until a valid value is saved. A saved value that the live policy no
  longer matches is re-applied at boot and hourly.
- **Size alert.** An optional budget in GB; the database size is checked every 10 minutes.
  Warning at 80 % and critical at 95 % of the budget or of the disk (when the control plane can
  read it: local database, `pg_read_all_settings`). For a database on the same host the
  installer grants `pg_read_all_settings` to the control plane's role on install and on every
  upgrade (as `postgres`, never prompting), then checks with the role's own connection. If the
  check fails, or the database is elsewhere, it prints `GRANT pg_read_all_settings TO wafio;` to
  run yourself; the page says so too. `… | sudo WAFIO_SKIP_SETTINGS_GRANT=1 bash` skips the grant
  (set after `sudo`, which drops the caller's environment; an upgrade otherwise re-applies it
  after a REVOKE). The role then reads every server setting,
  with no file or data access; that includes a secret written inline into a setting, such as
  a password in `primary_conninfo` or a passphrase in `ssl_passphrase_command`, so keep those
  in a passfile or script. The page shows growth, a projection and "full
  in N days". A banner appears on every Administration page, system admins get a header
  indicator, and an email goes to every system admin when a level is first reached (once per
  level per 24 h, only with a mail server configured).
- **Metrics.** `wafio_db_size_bytes`, `wafio_db_size_budget_bytes`, `wafio_db_size_alert_level`,
  `wafio_db_growth_bytes_per_day`, `wafio_db_filesystem_free_bytes`, `wafio_retention_days`,
  `wafio_retention_active`, `wafio_retention_deleted_total`.
- **API.** `GET /api/admin/storage`, `GET /api/admin/storage/alert`,
  `PUT /api/admin/storage/retention`, `PUT /api/admin/storage/budget`; changes are audited
  (`admin.retention_updated`, `admin.storage_budget_updated`).

## Known limits

- After a trace rule or correlation chain changes, a batch built between the write and the
  arrival of the new filter (one round trip) still uses the old one. An event the change would
  newly store can be lost in that window. When more than 4,096 projects have changes waiting,
  a rule read fails, or an agent that connected without a host was linked to one after it
  connected and has sent no batch since, the change goes out with the agent's next batch instead
  (about one batch interval).
- Decision redaction goes by name. A credential under a name that does not match (a custom
  header such as `X-Customer-Ref`, a session cookie named after the app) is redacted only when
  it is in `Cookie` or `Authorization`, which are dropped. A decision that does not name its
  input exactly (CRS and custom rules, `body`, `body.json`, `query`, WebSocket frames, older
  WAF agents) also redacts a credential-named header, parameter or field that carried the
  payload; `match_detail` still names the detection.
- When an engine flags a real credential by mistake (a false positive on a password), the value
  is kept: the engine named it. Only the JWT engine and the entropy anomaly heuristic are
  treated as credential checks.
- The control plane cannot tell which value of a repeated credential name was flagged, and
  does not know whether a stored body copy was cut when the agent decoded it (gzip): it then
  keeps only values that look like an attack, so an engine-flagged value that does not (some
  NoSQL or SSRF values) is redacted there although the agent kept it. A flagged value longer
  than the stored copy, or a header value the engine scanned cut, is redacted too.
- JSON nested deeper than 64 levels is redacted wholesale: every value below that depth
  becomes `[redacted]` (keys stay). JSON inside a form field (`data={"password":…}`) and XML
  bodies are not parsed for redaction.
- The body preview of the legacy HTTP ingest has no match source, so every credential-named
  field is redacted.
- Under contention, someone who controls several accounts still gets one share per account.
  The process-wide total holds however many accounts there are. Each share now has to be paid
  for on the wire, at up to 64 inflated bytes per byte sent.
- An account that had to wait in the last 2 s counts as wanting a full share. One burst just
  over its budget every 2 s, about half a share of traffic, is enough to hold a whole share.
- There is no minimum share per account and heartbeats do not skip the budget. Every active
  account already gets at least total ÷ active accounts, and throttled agents stay online.
- The fair share is per control plane process.
- An account at its budget has its heartbeats delayed. Its agents stay online, but their
  heartbeat data (host info, counters) arrives late.
- Without a viewer, host status, metrics, trace statistics and rule hit counts shown on Fleet
  and Overview or exported through OpenMetrics can be about 30 s old (the agent checks on a 3 s
  tick, so up to ±32 s). Agent-side state changes other than a configuration apply reach the
  control plane as late. The first metrics sample after a page opens averages the idle gap.
- A process that names itself `node`, `java` or another JIT runtime gets MEDIUM, not CRITICAL,
  for its RWX `mprotect`, and opens no incident for it. Its other events keep their severity.
