# Wafio v2.0.0 release notes (control plane)

Released on 18 November 2026. This file lists what the control plane of v2 changes for an operator and for the dashboard.

WAFio v2 ships the Rust WAF agent only. The Go WAF agent and the OWASP CRS rule set (Coraza) are gone.

The installers (`deploy/install*.sh`), the bundle layout (`deploy/BUNDLE.md`), the WAF agent unit, `scripts/release.sh` and
`scripts/publish-release.sh` named below are in the wafio-release repository, not in this one.

## Upgrade

- The WAF agent is two files: the open agent and the engine library `libwafio_semantic_engine.so`. `scripts/release.sh` takes
  them with `--waf-agent` and `--engine-lib` (one binary with the engine linked in needs `--linked-in`, the open agent alone needs
  `--open-build`). The installers put the library at `/usr/lib/wafio` (root, mode 0644, with its `.sha256`) and set
  `WAFIO_ENGINE_LIB_REQUIRED=1` in `/etc/wafio/waf-agent.env`, so an agent whose library is missing or damaged does not start.
  An upgrade from a v1 install or from a single binary installs the library and the setting.
- The WAF agent bundle holds the Rust agent, which `scripts/release.sh` takes with `--waf-agent <binary>`, and `scripts/publish-release.sh`
  refuses a WAF agent bundle whose `NOTICES.txt` has no section "Code adapted from other projects", so a Go agent bundle of an
  earlier release cannot be published again.
- A Go agent cannot reload into the Rust agent without a restart. The first upgrade and a rollback restart the agent.
- From version 1.10 the control plane applies four additive migrations, 000115 to 000118. `000115_agents_rule_engine` adds the
  nullable column `agents.rule_engine`; no code reads or writes it any more. `000116_agents_script_rules` adds the nullable column
  `agents.script_rules`, whether the agent can run script rules, taken from its Hello. `000117_waf_decisions_status` adds the
  nullable column `waf_decisions.status` (the HTTP status the client received); it has no default and rewrites no chunk.
  `000118_runtime_noise_calibration` adds fifteen built-in Runtime Security rules to every host (see Runtime Security below); it
  changes and deletes no existing rule. Nothing is dropped or rewritten: the columns `project_configs.crs_dir` and
  `agents.rule_engine` and the history columns stay, and no code reads or writes the first two.
- The control plane no longer reads `crs.*` or `WAFIO_CRS_*`. A `config.yaml` or an environment that still sets them boots as before.
- The WAF agent reads its security-data directory from `WAFIO_SECURITY_DATA_DIR` (flag `--security-data-dir`), the directory itself.
  v1 wrote `WAFIO_CRS_DEFAULT_DIR`, `WAFIO_CRS_SETUP_FILE` and `WAFIO_CRS_RULES_GLOB` into the agent's env file. The installers now
  write only `WAFIO_SECURITY_DATA_DIR`, and a re-run removes the three old lines. When the file has no `WAFIO_SECURITY_DATA_DIR`
  yet, it takes the directory the old `WAFIO_CRS_DEFAULT_DIR` pointed into (`<dir>/crs`, `<dir>/crs/coreruleset` or
  `<dir>/crs/coreruleset/rules` give `<dir>`). An env file the installer has not touched still works: the agent derives the
  directory from the old variable and logs one warning.
- `wafio fetch-data` and Administration > Security data no longer download the rule set. `--crs-version` is gone from `fetch-data`;
  a request that still names `crs` selects no component for it.
- The Go detection engines are gone from this repository: `wafio rule-test`, `cmd/wafio-script-sidecar`, `tools/wafbench`,
  `tools/gencorpus`, the request analysis of `internal/application` and the payload corpus with its tests. Detection is the
  WAF agent's alone. `internal/engine` keeps what the control plane needs: loading, validating and normalising `rules_json`,
  the checks on custom and script rules, the default pages and the bot lists.
- The WAF agent reports one capability in its Hello: `script_rules` when it can run script rules, `no_script_rules` when it
  cannot (a version 1 Go agent without scripts). The bundle no longer depends on what an agent reports: every agent gets the same
  bundle. A v1.x Go agent older than v1.9 does not know `jwt` and `graphql` in a path override or in `skip_semantic`, so it refuses
  a bundle that names them and keeps serving its cached bundle until it is upgraded.
- `Welcome.agent_id` is `agents.id`, the id the dashboard and the API show, not the id of the credential.
- `deploy/install.sh` checks the Ed25519 signature of a bundle with OpenSSL when this OpenSSL can verify Ed25519 from its command
  line (3.0 and later) and with a verifier in python3's standard library when it cannot. OpenSSL 1.1.1 (AlmaLinux 8, Debian 11,
  Ubuntu 20.04) cannot, and the installer used to refuse to install there. An OpenSSL that can verify decides alone: a
  refusal by it is final. The portal serves a copy of `deploy/install.sh`; it carries the fix once it is deployed.
- `systemctl stop wafio-waf-agent` after a `systemctl reload` ends the agent cleanly. Before, systemd sent SIGKILL at once,
  because the process a reload leaves as the main process is not its child. The unit has an `ExecStop=` that sends SIGTERM to
  the main process and its children and waits (see `deploy/systemd/README.md`); the inline units of the installers have it too.
  A host that holds the unit of an earlier build gets it with the next install.
- `deploy/install.sh` follows the order that `deploy/BUNDLE.md` describes for a WAF agent upgrade. It writes the library and the
  agent binary under temporary names beside their destinations, and runs the staged agent with `--features --engine-lib
  <staged library>` in a clean environment, before it stops any service; a library the agent cannot load is refused with the
  host as it was. Only then does it stop the agent and rename the library and the binary into place. Before, it wrote the
  binary over its destination after the stop and removed it first when that failed, which could leave a new library, no binary and
  a stopped agent. When the WAF agent was running and a later step fails (migrations, accounts, credentials), the installer starts
  it again when the binary and library in place are a pair, and says which pair and that the install did not finish. The bundle
  installer runs the same check of the staged pair.
- `deploy/install.sh` stops when a bundle cannot be unpacked whole (it used to go on with what had been extracted). The WAF agent
  and host agent bundle installers no longer fall back to a binary in the working directory or in `/tmp`: a bundle without its
  binary is an error. The control plane installer no longer falls back to `/tmp` (it still takes the binary from the working
  directory, where its README has it run).
- The env files the installers write are read with the white space before a name ignored, as systemd does: a line such as
  ` WAFIO_ENGINE_LIB_REQUIRED=0` is the operator's value and stays. The bundle installer no longer joins a new key to a last line
  that had no newline.
- A bundle without a library (`--open-build`, the engine linked in) installed over a pair leaves the library and
  `WAFIO_ENGINE_LIB_REQUIRED=1` in place, and the installers warn about both and how to remove them.
- `scripts/release.sh` refuses an agent and a library that are not in one build directory.
- The installers and the release scripts moved out of this repository into wafio-release. Each repository now builds only its
  own part (`scripts/build-dist.sh` here and in wafio-agent-host, which write `dist/controlplane/` and `dist/host-agent/` with
  `VERSION` and `SHA256SUMS`), and `scripts/release.sh` of wafio-release makes, signs and uploads the three bundles from those
  parts (`--controlplane`, `--waf-agent`, `--host-agent`). The upload target is named by `WAFIO_RELEASE_HOST` and
  `WAFIO_BUNDLES_DIR`; `WAFIO_REMOTE_HOST` no longer names it.
- The control plane and the host agent are no longer built with garble. Their source is open, so obfuscation hid nothing; the
  release binaries are plain `go build -trimpath` builds. The `--no-garble` option is gone with it.
- `scripts/release.sh` packs every bundle with owner and group 0 and no group or other write bit. A bundle built before this
  change carries the uid of its build user and group-writable modes: rebuild it before it is published.
- `deploy/install.sh` counts Amazon Linux (`ID=amzn`) as the RHEL family. openSUSE Leap still prints "Unrecognized OS": the
  installer's package names are those of Debian and of the PostgreSQL and TimescaleDB repositories for RHEL, and none of them
  maps to zypper without separate repository set-up, so dependency auto-install stays off there. The agent install does not need it.

## What happens to stored configuration

Nothing is rewritten in the database. A project or application configuration written by v1 loads, displays, saves again and
produces a valid bundle. Every save, every read for the editor and every bundle sent to an agent rewrites these keys:

| Key | Result |
|---|---|
| `request_body_in_memory_limit`, `response_body_limit` | removed (no agent applies them) |
| `semantic_policies.skip_coraza_when_clean` | removed, whatever it holds; the agent always behaves as if it were `true` |
| `disable_semantic` and `disable_rule_based`, in `semantic_policies` and in a path exception | one key, `inspection_off` |
| `disable_semantic: true`, alone or with `disable_rule_based` | becomes `inspection_off: true` |
| `disable_rule_based` alone | removed (it did nothing without the rule set) |
| `thresholds` | removed; when its effective log value is not below its block value, `semantic_policies.record_weak_detections` becomes `false`; with bot protection in `score` mode the block value becomes `bot_protection.score_threshold` |
| `semantic_policies.<engine>.base_score` (also in a path `semantic_override`) | removed; a `0` becomes `disabled: true` on that engine (not on the four engines that only switch) |
| `categories.<name>.base_score` | removed; a `0` becomes `disabled: true` on each engine that falls back to the category and has no `base_score` of its own; an empty category is removed, and `categories` with it |
| path `rule_override` (`log_threshold`, `block_threshold`, `categories`) | removed |
| `effect.weaken` of a custom tuning rule or of path tuning | removed; a multiplier below 1 or a positive block delta becomes `effect.action: "log"`, any other `weaken` is dropped |
| path tuning `effect.skip_crs` | removed |
| custom tuning rule with engine `crs` | left out of the bundle |
| custom tuning rule `scan_mode: crs_only` or `semantic_only` | read as `default` and stored as `default` |
| custom tuning rule `skip_semantic ["*"]`, `scan_mode: disabled` | unchanged: inspection off for the matched requests |
| `sensitivity` in a save | ignored; 2 is stored and answered |
| categories RFI, Method, Generic, Scanner, Protocol, Multipart, SessionFixation, and `sensitivity`, `confidence`, `disabled` of any category | accepted and ignored; the default document leaves them out |

The default document, and so a new project, has none of these keys, and a save of the unchanged default changes nothing.

A detection is strong (it blocks) or weak (it logs); a document holds no score threshold and no base score. Three keys replace them:

| Key | Meaning | Default |
|---|---|---|
| `semantic_policies.record_weak_detections` | `false` lets a weak detection through without a decision row | `true` (absent) |
| `bot_protection.score_threshold` | in `score` mode, the bot score at which a request blocks, 1 to 9999 | `150` (absent) |
| `effect.action` of a tuning rule or path tuning | `"log"` records a blocking detection of a matched request as LOG and lets it through; the only value | none |

A decision row and a live decision event carry `strength`: `"block"` for a block or monitor decision and for a LOG that held a
blocking detection back (`engines_log_only` is not empty), `"weak"` for a LOG with a category that would not have blocked, `null`
otherwise. `score` stays on rows and events.

The old guard that refused settings which left a semantic-only agent inspecting nothing is gone, with its error code
`SEMANTIC_ENGINES_REQUIRED`. Script rules keep their guard (`SCRIPT_RULES_UNSUPPORTED`).

## Save validation

A save answers 400 `INVALID_RULES`, naming the path of the key and saying to remove it, for an unknown key under `semantic_policies` and
for an engine field that does nothing: a `block_threshold` or `soft_threshold` under `header_injection`,
`open_redirect`, `prompt_injection`, `anomaly`, `jwt` or `graphql` (they take `disabled` and `action` only). It also refuses a
`record_weak_detections` that is not `true` or `false`, a `bot_protection.score_threshold` that is not a whole number from 1 to
9999 and a tuning `action` other than `log`, naming the key. The legacy keys of the table above are rewritten before this check and
never refused. A stored
document that carries such a key still loads and the agent ignores it, so an old document is cleaned before it is saved again.

## Engine switches

The per-engine switches stay. `semantic_policies.<engine>.disabled`, a path rule's `semantic_override.<engine>.disabled` and the
names in `skip_semantic` (path tuning and custom tuning rules, `"*"` for all) take twenty keys: `sql`, `xss`, `cmd`, `php`, `python`,
`lfi`, `ssrf`, `java`, `nosql`, `ssti`, `xxe`, `deser`, `ldap`, `proto_pollution`, `jwt`, `graphql` and, new, `header_injection`,
`open_redirect`, `prompt_injection` and `anomaly`. The key of the switch is `disabled`; there is no `enabled` key. A Rust agent built
before the four new keys were added refuses a bundle that names them in a path override or in `skip_semantic`.

Each engine key also takes `action`: `block` (the default, the same as no key) or `log`. A key set to `log` still detects and records,
and never blocks: what it would have blocked becomes a LOG decision with the same category, score and match detail, the request is
forwarded, and the decision lists the key in `engines_log_only`. It is meant for a site that is being tuned. `semantic_policies.<engine>.action`
sets it for the project and a path rule's `semantic_override.<engine>.action` for a path (an absent action inherits the project's;
`disabled` wins over it). A request that another engine still on `block` also detects is blocked. A held block does not count toward the
block policy or the IP jail. A save refuses any other value and names the key. The Rust WAF agent applies it; an older agent ignores the
key and blocks.

A decision lists the engines the operator switched off for it. The API returns them as `engines_off`, an array of keys (empty when
none), and `coverage` keeps only the gap flags. Rows written by an earlier agent carry `engine_disabled:<key>` among the gap flags of
`coverage`; the API splits them on read, and the stored rows are not rewritten. An engine switched off is information, not a gap.

## API

- Removed from the API: `rule_engine` (agent answers: fleet agent, fleet agent list, application agent); `rule_based_triggers`
  and `hybrid_triggers` (stats and summaries: their counts are in `semantic_triggers`); `body_limit_bytes` of a route and of
  `GET /api/internal/waf/bundle`; `exclude_rules` of that bundle. The columns `agents.rule_engine` and `project_configs.crs_dir`
  stay and are not read.
- `analyze_method`: `rule_based`, `hybrid` and the SIEM spelling `rule-based` read as `semantic`, at ingest and on every read of a
  stored row. Stats count them as `semantic_triggers`, and the by-method breakdowns list them under `semantic`. Stored rows are
  not rewritten.
- New on decision rows (lists and the live event): `status`, the HTTP status the client received, `0` meaning not recorded (a row
  of an earlier agent, or an event the agent has no status for), `engines_off` and `engines_log_only`.
- `GET /api/internal/waf/bundle`, which no agent calls, rewrites the legacy keys of the `rules_json` it returns like a bundle on
  the stream does.
- `paranoia` is no longer in a route or in the agent bundle.
- The security data component `crs` is gone from the status answer. A v1 agent that still lists it is ignored.
- SIEM events carry no `rule_ids` and no `rule-based` label any more.
- `api/openapi.yaml` lists every removed and ignored key in the `WafRulesJson` schema.

## Runtime Security

An ordinary Ubuntu 24.04 workstation stored HIGH and CRITICAL events for its own routine: every `sudo` and `cron` run
(CRITICAL, a read of `/etc/shadow`), a desktop tool running `ps e` four times a second (700,000 HIGH rows in 15 minutes),
`docker run` (HIGH mounts, chowns and a BPF load by the container runtime) and every `ping` (HIGH, a raw ICMP socket). They are
now stored at MEDIUM, which opens no incident, and tagged `unverified-identity`, because a process chooses its own name:

- `sudo`, `sudoedit`, `su`, `runuser`, `doas`, `pkexec`, `cron`, `crond`, `atd` and `login` reading `/etc/shadow` or `/etc/gshadow`
  read-only (rule "Downgrade auth helper shadow reads"). The event carries the real UID, so a set-user-ID `sudo` was rated like an
  unprivileged reader.
- `ps`, `top`, `htop`, `btop`, `pgrep`, `pkill`, `pidof`, `procs`, `glances` and `systemd-cgls` reading `/proc/<pid>/environ`
  read-only (rule "Downgrade process viewer environment reads").
- A program reading the credential file of its own tool in a user's home directory (`ssh` and `~/.ssh/id_*`, `docker` and
  `~/.docker/config.json`, `aws`, `az`, `gpg` and the like; `/root/...` for UID 0). This is done in the classifier, not by a rule, so
  it has no switch. Any other reader, and a reader of another tool's file, keeps CRITICAL.
- The container runtime at `docker run`: `runc` mounting its own `/proc` descriptors, the masked and read-only `/proc` paths and
  files under `/var/lib/docker`, `/var/lib/containerd` and `/run/containerd`; `dockerd` and `containerd` changing the owner to root
  under the first two (LOW when the agent verified the binary); `runc` loading its device cgroup BPF program. A host path mounted
  into a container, and the same events from another parent, keep HIGH. Rules: "Downgrade container runtime setup mounts",
  "Downgrade verified container daemon chown", "Downgrade container daemon chown", "Downgrade runc cgroup device BPF program".
- `ping`, `ping6`, `traceroute`, `mtr` and `arping` creating their raw socket (rules "Downgrade ICMP raw socket by network tools" and
  "Downgrade arping raw packet socket"). Any other raw socket keeps HIGH.

A write, and an open that an agent reports as failed, keep the severity they had. The host agent reports the result of an open in
`ret_val`, negative for a failure, and the description of such an event says "failed to open". An open that reached no file
(`ENOENT`, `ENOTDIR`) is not counted as an access to a credential, because `ssh` tries every default identity file on each
connection; a refusal (`EACCES`, `EPERM`) stays a failed access. An open the agent could not pair with its result carries
`ret_val` 0.

Detection rules gain the field `ret_val` and the operator `starts_with_any` (`api/openapi.yaml`, `RuleCondition`).
`TraceForwardRevision` is 3: a host agent built before it stops applying the forwarding filter and sends every event until it is
upgraded.
