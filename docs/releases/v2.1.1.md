# Wafio v2.1.1 release notes

Released on 19 November 2026. This is a security release of the WAF agent. The control plane, the dashboard and the host agent
stay at v2.1.0: their v2.1.0 bundles are published again, signed for v2.1.1.

## Upgrade

- Upgrade the WAF agent on every host that serves an application with an `fcgi:` upstream:
  `curl -fsSL https://wafio.cloud/install.sh | sudo bash -s -- waf-agent`.
- There is no migration and no control plane change. A v2.1.1 WAF agent works with a v2.0.0 or v2.1.0 control plane.
- Hosts whose applications all use HTTP upstreams are not affected by the change below, but get the same agent.
- WAF agents of the 1.x line keep FastCGI connections open as well and get no update. Move them to 2.1.1.

## Security

### FastCGI upstreams no longer keep the connection to PHP-FPM open

- Up to v2.1.0, the WAF agent sent `FCGI_KEEP_CONN` to PHP-FPM and kept its connections in a pool for later requests.
- With a PHP-FPM release that lacks the fix for CVE-2026-129289 (GHSA-qc49-hpvq-g2w6), a kept connection is unsafe.
  An attacker can send a request whose body the application does not read to the end, and PHP-FPM runs the unread bytes as a
  second FastCGI request with code chosen by the attacker. The fix is in PHP 8.2.36, 8.3.37, 8.4.28 and 8.5.13, each for its own
  series. 8.1 and older get no release from the PHP project.
- The agent also read the reply records without checking their request id. A reply left on a kept connection could be taken as
  the reply to the next request on that connection.
- v2.1.1 sends no `FCGI_KEEP_CONN`. It opens a connection for each request and closes it after the reply, as nginx does by default
  (`fastcgi_keep_conn off`). The limit on concurrent connections to one upstream stays.
- A reply record with another request id fails the request.
- A request whose write to PHP-FPM fails is no longer sent a second time on a new connection. That retry could run a `POST` twice.
- Update PHP as well. This release closes the path through the WAF agent; it does not fix PHP-FPM, and any other front end that
  reuses FastCGI connections stays exposed.

## Changed

- `idle_conn_ms` no longer applies to FastCGI routes, because they keep no idle connections. It still applies to HTTP upstreams.
- Each FastCGI request now costs one connect. Over a Unix socket that is cheap. A TCP `fcgi://` upstream under heavy load holds
  more sockets in `TIME_WAIT` than before.
- A later release adds a per-application option to keep FastCGI connections open again, for PHP releases that carry the fix.
